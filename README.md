# Career Radar

![CI](https://github.com/Timir-UR/career-radar/actions/workflows/ci.yml/badge.svg)

Агрегатор удалённых вакансий с упоминанием Python. Проект собирает объявления из Remotive и SuperJob в фоновом режиме, приводит их к единому формату и сохраняет в PostgreSQL без повторов. Веб-интерфейс позволяет искать вакансии, комбинировать фильтры и переходить к исходному объявлению.

![Главная страница Career Radar](docs/2026-09-25_13-52-30.png)

## Возможности

- Два источника, у каждого своя задача Celery, своё расписание и свои настройки повторов: Remotive раз в 12 часов, SuperJob раз в час.
- Отбор по упоминанию Python: у Remotive — локальной проверкой названия и описания, у SuperJob — параметром `keyword` на стороне их API.
- Дедупликация по содержимому при пакетной вставке в PostgreSQL. Одна и та же вакансия, размещённая на обеих досках, сохраняется один раз.
- Полнотекстовый поиск по названию вакансии и компании.
- Фильтры по региону, компании и минимальной зарплате.
- Загрузка вакансий порциями по 20 без перезагрузки страницы через HTMX.
- JSON API и интерактивная документация FastAPI.
- Прогон линтера и тестов на каждый push через GitHub Actions.

## Архитектура

```mermaid
flowchart TD
    Beat[Celery Beat] --> MQ[RabbitMQ: очередь задач]
    MQ --> Worker[Celery Worker]

    Worker --> TaskR[collect_remotive: раз в 12 часов]
    Worker --> TaskS[collect_superjob: раз в час]

    TaskR --> Common[collect_data: общая логика сбора]
    TaskS --> Common

    RemotiveAPI[Remotive API] --> CollR[Коллектор Remotive: локальный фильтр, срез 50]
    SuperjobAPI[SuperJob API] --> CollS[Коллектор SuperJob: keyword и count на стороне API]

    Common --> CollR
    Common --> CollS

    CollR --> NormR[normalize_remotive]
    CollS --> NormS[normalize_superjob]

    NormR --> Schema[Схема NormalizeVacancy: проверка типов]
    NormS --> Schema

    Schema --> Storage[SHA-256 и INSERT ON CONFLICT]
    Storage --> DB[(PostgreSQL 16)]

    Browser[Браузер / HTMX] --> API[FastAPI]
    API --> DB
    DB --> API
    API --> Templates[Jinja2: HTML-фрагменты]
    Templates --> Browser
    API --> JSON[JSON API]
```

В Docker Compose пять сервисов: `api`, `db`, `rabbitmq`, `worker` и `beat`. Beat отправляет в брокер два разных задания по двум расписаниям, worker выполняет их независимо друг от друга: сбой одного источника не отменяет сбор другого и не влияет на его повторы. Веб-приложение читает уже собранные данные из базы: поиск на сайте не обращается к внешним API.

Общая функция `collect_data(source_name)` написана один раз и про конкретные источники ничего не знает — коллектор и нормализатор выбираются по имени источника в начале функции. Всё, что идёт после схемы `NormalizeVacancy` — хеширование, вставка в базу, полнотекстовый поиск, фильтры, страница — работает с обоими источниками без изменений. Добавление SuperJob не потребовало правок ни в одном из этих мест.

## Запуск через Docker Compose

Нужны Docker с поддержкой Linux-контейнеров и Docker Compose v2. На Windows подходит Docker Desktop. Все команды выполняются из корня репозитория. Для сборки образов, сбора вакансий и загрузки HTMX с CDN нужен интернет.

### 1. Получить ключ SuperJob

Remotive работает без авторизации, SuperJob требует ключ. Зарегистрируйте приложение на [api.superjob.ru/register](https://api.superjob.ru/register/) и возьмите значение Secret key из параметров доступа. Ключ передаётся в заголовке `X-Api-App-Id` и ограничен 120 запросами в минуту с одного адреса IP.

### 2. Настроить окружение

Создайте `.env` из примера, если файла ещё нет. Существующий `.env` перезаписывать не нужно.

PowerShell:

```powershell
Copy-Item .env.example .env
```

Bash:

```bash
cp .env.example .env
```

Задайте `POSTGRES_PASSWORD` и `SUPERJOB_SECRET_KEY` в `.env`. Файл содержит следующие настройки:

| Переменная | Значение в примере | Назначение |
| --- | --- | --- |
| `POSTGRES_USER` | `radar` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | `change_me` | Пароль PostgreSQL |
| `POSTGRES_DB` | `radar` | Имя базы |
| `POSTGRES_HOST` | `localhost` | Хост базы при запуске Python локально |
| `POSTGRES_PORT` | `5432` | Порт PostgreSQL |
| `RABBITMQ_URL` | `amqp://guest:guest@localhost:5672//` | Адрес брокера при локальном запуске |
| `SUPERJOB_SECRET_KEY` | `your_superjob_key_here` | Секретный ключ приложения SuperJob |

Файл `.env` перечислен в `.gitignore` и `.dockerignore`: он не попадает ни в репозиторий, ни в образ. В контейнеры переменные приходят через раздел `env_file` в `docker-compose.yml`.

Поле `SUPERJOB_SECRET_KEY` объявлено в классе `Settings` обязательным. Если переменная не задана, контейнеры не поднимутся: `pydantic-settings` бросит `ValidationError` при импорте настроек. Это сделано намеренно — лучше не запуститься с внятным сообщением, чем упасть через час посреди сбора.

В контейнерах Compose автоматически заменяет хост PostgreSQL на `db`, а адрес RabbitMQ — на `rabbitmq`. Внутренний порт PostgreSQL оставьте `5432`. Пароль с обычными буквами и цифрами позволяет избежать особенностей обработки специальных символов текущей конфигурацией Alembic.

### 3. Подготовить базу и применить миграции

```bash
docker compose up -d db rabbitmq
docker compose build
docker compose run --rm api alembic upgrade head
```

Миграции создают таблицы `sources` и `vacancies`, включённый источник `remotive`, вычисляемое поле полнотекстового поиска и GIN-индекс. При обычном старте контейнеров миграции автоматически не выполняются.

Источник `superjob` миграцией пока не заводится, его нужно добавить один раз вручную:

```bash
docker compose exec db psql -U radar -d radar -c "INSERT INTO sources (name, type, base_url, enabled) VALUES ('superjob', 'api', 'https://api.superjob.ru/2.0/vacancies/', true);"
```

### 4. Запустить приложение и первый сбор

```bash
docker compose up -d
docker compose exec worker celery -A app.tasks.celery_app call app.tasks.collect.collect_remotive
docker compose exec worker celery -A app.tasks.celery_app call app.tasks.collect.collect_superjob
docker compose logs --tail=100 worker
```

Команда `call` ставит задачу в очередь и возвращает её идентификатор. Завершение сбора и число новых вакансий смотрите в логах worker — каждая строка начинается с имени источника в квадратных скобках. Первый сбор запускается вручную, чтобы не ждать очередного задания Beat.

Откройте:

- [Веб-интерфейс](http://localhost:8000/).
- [Swagger UI](http://localhost:8000/docs).
- [Health endpoint](http://localhost:8000/health) — проверяет ответ приложения, но не состояние базы и брокера.
- [RabbitMQ Management](http://localhost:15672/) — локальные учётные данные `guest` / `guest`.

Порты сервисов привязаны к `127.0.0.1`. Данные PostgreSQL хранятся в Docker volume `pgdata`.

После первоначальной настройки обычный запуск выполняется одной командой:

```bash
docker compose up -d --build
```

## Поиск и фильтрация

Веб-форма объединяет полнотекстовый запрос с фильтрами по региону, компании и зарплате. HTMX запрашивает `/partials/vacancies` при отправке формы и после 400 мс без ввода, затем заменяет список HTML-фрагментом. Кнопка «Показать ещё» добавляет следующую порцию с текущими фильтрами.

Поиск использует `websearch_to_tsquery('english', q)` и оператор `@@`. Поле `search_vector` имеет тип `TSVECTOR`, вычисляется PostgreSQL из `title` и `company` и хранится с GIN-индексом. Описание вакансии в полнотекстовый поиск не входит.

Примеры запросов:

| Запрос | Значение |
| --- | --- |
| `python senior` | Оба слова |
| `python -junior` | Python, исключая junior |
| `python OR django` | Одно из слов |
| `"software engineer"` | Фразовый поиск с учётом обработки слов PostgreSQL |

Регион и компания фильтруются через `ILIKE '%значение%'`, без учёта регистра. Поле `city` заполняется по-разному в зависимости от источника: у Remotive это `candidate_required_location` — страна, регион или `Worldwide`, а не обязательно город; у SuperJob это поле `title` вложенного объекта `town`, то есть настоящий город на русском. Поэтому один и тот же фильтр по региону работает с латиницей для одного источника и с кириллицей для другого.

Зарплатный фильтр проверяет `salary_min >= указанное значение` и исключает записи с неизвестной зарплатой. Заполнена зарплата только у части вакансий SuperJob: у Remotive она не разбирается вовсе, у SuperJob значение `payment_from` равно нулю примерно в 85% объявлений и превращается нормализатором в `NULL`.

Результаты сортируются по времени первого сохранения, затем по ID, новые сверху. Это не сортировка по релевантности или дате публикации источника.

### JSON API

| Метод и путь | Параметры | Ответ |
| --- | --- | --- |
| `GET /vacancies` | `city`, `company`, `salary_min`, `limit`, `offset` | Массив вакансий с фильтрами |
| `GET /vacancies/search` | обязательный `q` от 2 символов, `limit`, `offset` | Массив результатов полнотекстового поиска |
| `GET /health` | — | `{"status":"ok"}` |

Для обоих списков `limit` по умолчанию равен 20, допустимый диапазон — 1–100; `offset` начинается с 0. В JSON API поиск и остальные фильтры разведены по двум маршрутам; комбинирование доступно в веб-форме.

```text
http://localhost:8000/vacancies?city=Europe&limit=20&offset=0
http://localhost:8000/vacancies/search?q=python%20-junior
```

## Сбор данных

Задачи `collect_remotive` и `collect_superjob` вызывают общую функцию `collect_data(source_name)`. Она выбирает коллектор и нормализатор по имени источника, проверяет флаг `sources.enabled` **до** похода в сеть, прогоняет сырые записи через нормализатор в цикле и сохраняет результат. Ошибки нормализации `KeyError`, `ValidationError` и `AttributeError` перехватываются внутри цикла: битая запись логируется и пропускается, остальные сохраняются. Время успешного прохода записывается в `sources.last_run_at` средствами PostgreSQL через `func.now()`.

Для каждого запуска внутри асинхронной функции создаются собственные engine и фабрика сессий; в `finally` выполняется `await engine.dispose()`. Это необходимо потому, что синхронная задача Celery вызывает `asyncio.run(...)`, а он создаёт и закрывает новый event loop на каждый вызов: соединение из пула привязано к тому циклу, в котором было открыто, и переиспользование между вызовами даёт `RuntimeError: Event loop is closed`. FastAPI такой проблемы не имеет, потому что Uvicorn держит один цикл на всё время жизни процесса, и использует отдельную фабрику сессий.

### Remotive

Коллектор выполняет `GET https://remotive.com/api/remote-jobs` без параметров, проверяет HTTP-статус и читает массив `jobs`. Для каждой записи объединяет название и описание, приводит текст к нижнему регистру и проверяет наличие подстроки `python`. Отбор вынесен в отдельную чистую функцию `filter_python_jobs`, которая не ходит в сеть и покрыта тестами. Срез `[:50]` применяется к результату отбора, а не к размеру полученного ответа.

Локальный отбор нужен потому, что публичный API Remotive игнорирует параметр поиска и всегда отдаёт ленту целиком. По их документации возвращаются все **активные** объявления — закрытые и заполненные из ленты исчезают. Лента небольшая: на момент написания 16 вакансий, поэтому срез 50 ни разу не срабатывал и служит предохранителем.

Remotive просит обращаться не чаще четырёх раз в сутки и блокирует при более чем двух запросах в минуту. Отсюда интервал 12 часов и `max_retries=1`: два запуска по две попытки дают ровно четыре обращения в сутки в худшем случае. Условия использования требуют указывать Remotive источником и вести ссылку на их страницу вакансии — это выполнено в блоке внизу страницы и в поле `url` каждой карточки.

### SuperJob

Коллектор выполняет `GET https://api.superjob.ru/2.0/vacancies/` с заголовком `X-Api-App-Id` и параметрами `keyword=python`, `count=50`, `page=0`, `order_field=date`, `order_direction=desc`. Отбор по слову делает сам источник, локального фильтра здесь нет; ограничение количества задаёт параметр `count`, среза в коде тоже нет.

Параметры сортировки заданы явно не для красоты: по умолчанию SuperJob сортирует не по дате, и без них нулевая страница наполняется по неизвестному правилу, а новые вакансии могут в неё не попадать. С явной сортировкой нулевая страница — пятьдесят самых свежих объявлений.

Поле `payment_from` приходит целым числом в рублях, причём ноль означает «зарплата не указана». Нормализатор превращает ноль в `NULL`, иначе на странице появились бы вакансии с зарплатой 0, а фильтр отсеивал бы их наравне с теми, у кого зарплата честно неизвестна. Поле `date_published` обновляется при поднятии вакансии работодателем, то есть означает дату последнего поднятия, а не создания; на дедупликацию это не влияет, потому что дата в хеш не входит.

Город приходит вложенным объектом `town`, работодатель — полем `firm_name` с запасным путём через `client.title` для анонимных объявлений. Если название компании пусто в обоих местах, нормализатор отдаёт `None`, схема бросает `ValidationError`, и запись пропускается: вакансия без работодателя бесполезна для показа и ломает дедупликацию.

Ограничение SuperJob — 120 запросов в минуту, поэтому интервал час и `max_retries=3` обходятся примерно в 0,06% разрешённого объёма.

## Дедупликация

Ключ вакансии — SHA-256 от строки `company|title|city`. Перед хешированием значения приводятся к нижнему регистру и очищаются от пробелов по краям; отсутствующий регион заменяется пустой строкой.

Повторы внутри одной полученной партии убираются словарём по хешу. Затем выполняется пакетная вставка:

```sql
INSERT INTO vacancies (...) VALUES (...)
ON CONFLICT (content_hash) DO NOTHING
RETURNING id;
```

Уникальное ограничение на `content_hash` защищает от повторных вставок на уровне PostgreSQL, в том числе при параллельных задачах. По `RETURNING id` считается количество действительно добавленных строк.

Источник и внешний ID в хеш не входят. Отсюда два следствия. Первое: объявление, размещённое и на Remotive, и на SuperJob, сохранится один раз — за ним закрепится тот источник, который успел первым. Второе: вакансия, поднятая работодателем с новой датой публикации, не создаёт дубликат, потому что дата в хеш не попадает.

Это стратегия пропуска дублей: повторная запись не обновляет зарплату, URL или `last_seen_at`.

## Тесты, линтер и CI

```bash
ruff check .
ruff check . --fix
pytest -v
```

Двадцать пять тестов, все модульные: они проверяют отдельные функции и не обращаются ни к базе, ни к брокеру, ни к сети, поэтому выполняются за доли секунды.

| Файл | Что проверяет |
| --- | --- |
| `tests/test_hashing.py` | устойчивость хеша к регистру и пробелам, различие хешей при разных данных, длина 64 символа |
| `tests/test_normalizer.py` | сопоставление полей Remotive, приведение числового ID к строке, обязательность названия |
| `tests/test_normalizer_superjob.py` | сопоставление полей SuperJob, превращение нулевой зарплаты в `None`, запасной путь к названию компании, отсутствие вложенного объекта `town` |
| `tests/test_collector.py` | отбор по слову `python` в названии и в описании, независимость от регистра, устойчивость к записям без полей |

Настройки Ruff и pytest лежат в `pyproject.toml`. Включены наборы правил `E`, `F`, `I`, `UP`, `B`; для файлов `app/api/` и `app/web/` отключено правило `B008`, которое ложно срабатывает на `Depends` в подписях FastAPI.

Рабочий процесс `.github/workflows/ci.yml` на каждый push поднимает чистую виртуальную машину, ставит зависимости из `requirements-dev.txt` и прогоняет линтер и тесты. Установка с нуля на пустой машине ловит расхождение между тем, что стоит локально, и тем, что записано в файлах зависимостей.

```bash
# Сколько вакансий от какого источника и у скольких есть зарплата
docker compose exec db psql -U radar -d radar -c "SELECT s.name, count(*), count(v.salary_min) FROM vacancies v JOIN sources s ON s.id = v.source_id GROUP BY s.name;"

# Временно отключить источник без правки кода
docker compose exec db psql -U radar -d radar -c "UPDATE sources SET enabled = false WHERE name = 'remotive';"

# Остановить сервисы, сохранив данные PostgreSQL
docker compose down
```

Исходники копируются в образ при сборке, тома с кодом нет. После изменения кода нужен `--build`; один `restart` не подхватит правки. Не добавляйте `-v` к `down`, если нужно сохранить базу.

Проверять изменения в задаче удобно на отключённом источнике: флаг `enabled` читается до похода в сеть, поэтому вся цепочка от брокера до базы проверяется, а квота источника не тратится.

Если список пустой, проверьте применение миграций и логи первого сбора. Сообщение вида `[superjob] Источник не найден в базе` означает, что не выполнена команда `INSERT` из раздела про миграции. После успешного сбора пустой результат также возможен при слишком строгих фильтрах или отсутствии новых подходящих записей.

## Текущее состояние и ограничения

- Отбор по подстроке `python` у Remotive может включать вакансии, где Python упомянут как дополнительный навык. У SuperJob отбор выполняет их поиск, и его правила нам неизвестны.
- Описание используется только при отборе и не сохраняется. Полный текст доступен по ссылке на исходное объявление.
- Зарплата Remotive не разбирается: их API отдаёт её свободным текстом в поле `salary` («$50,000 - $70,000», «Competitive», часто пустая строка), числового поля нет. Валюта и период выплат не нормализуются ни для одного источника: в базе лежат рубли SuperJob без пометки о валюте.
- У SuperJob берётся только первая страница выдачи — около 40 записей из примерно 110 по запросу. Явная сортировка по дате гарантирует, что новые объявления не теряются, но уже существующие старые в базу не попадут. Постраничный обход делается циклом по параметру `page` до поля `more` в ответе и требует предохранителя от бесконечного цикла.
- Удаление закрытых вакансий и обновление существующих записей не реализованы. Источники отдают только активные объявления, поэтому в базе накапливаются вакансии, которых в лентах уже нет. Лечится переходом на `ON CONFLICT DO UPDATE` с обновлением `last_seen_at` и фильтром по свежести на странице.
- Колонка `sources.base_url` заполнена, но кодом не читается: адреса зашиты в коллекторах константами.
- Фильтра по источнику на странице нет, хотя `source_id` у каждой вакансии сохраняется.
- Процессы в контейнерах работают от пользователя root, о чём Celery предупреждает при каждом старте.
- Проект не развёрнут: запуск предполагается локальный, через Docker Compose.
